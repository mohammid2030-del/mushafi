# In-app Android updates (introduced in 3.1.6 / code 156)

The native updater checks the public HTTPS `/api/app-update` feed on the Mushafi website. Automatic checks are limited to one per 12 hours (failed checks retry after one hour); More also provides a manual check. Automatic offers appear only on Home/More, after onboarding, without interrupting the reader or another panel, and at most once per release per day. Existing 3.1.5 installations must manually install 3.1.6 once to acquire this feature.

The native controller owns the fixed server and download paths. It rejects unsupported SDKs and non-newer version codes. Downloads are streamed to app-private cache, bounded by the expected size, and verified against the full SHA-256. Before installation, Android's package parser must report the expected application ID/version and the exact same current signer set as the installed app. File verification runs again before an installer intent is opened. Invalid and partial files are removed; no user Quran, khatma, settings or account data is cleared. Cancellation stops the download. Closing the sheet leaves downloading active while the Activity survives; destroying the Activity stops it safely.

Android asks the user to allow installation from Mushafi when necessary, then asks to confirm the installation. FileProvider exposes the verified cached APK only through a read-granted content URI. The updater does not perform silent installs and is not an FCM/background push system. It is intended for the direct APK distribution channel; review store policies before enabling this permission in any future store build.

For a new release: increase both versionCode and versionName; build with the existing signing key; verify the signing fingerprint; upload the exact APK; publish matching code/name/package/minSdk/size/SHA-256/HTTPS URL and localized notes in the website feed. Never publish a ready update before its file exists and passes checksum verification. The temporary upload handler and runtime secret must be removed after publication. Keep previous download URLs valid.

Checks run for 3.1.6: required Gradle release validations and signed APK assembly; JVM metadata/downgrade/SDK/URL and tamper/truncation checks; Arabic and English WebView UI checks through a native bridge mock for check/download/progress/cancel/install callbacks, stable controls and no automatic interruption while reading; signing certificate continuity against 3.1.5. No Android emulator or device is available in this execution environment, so the Android Settings/installer screens have not been exercised on hardware.

## 3.1.8 refinements
Fresh automatic check on app launch, with a one-minute in-process guard for rapid visibility changes. A new-release offer includes localized notes, Update now/Later, and a reminder that More remains available. It defers during reading or other dialogs; Later suppresses repeats for that foreground session, resetting on the next launch or after more than one minute in the background. Reduced-motion preferences are honored.

Large downloads use three disjoint HTTP byte ranges when the server advertises range support. Each chunk retries independently and resumes at its durable offset. Chunks are isolated by the release SHA-256 and survive network errors, cancellation and Activity recreation. A sequential fallback supports servers without ranges. The merged APK must still pass full size/hash/package/version/signer checks before installation; invalid chunks are discarded. The UI shows received bytes and measured average transfer speed. Parallelism cannot guarantee a particular speed on every network.

JVM DownloaderChecks verifies overlapping parallel requests, interrupted range retry, persistent resume after cancellation, sequential fallback and rejection of mismatched Content-Range. Browser checks cover automatic offers, notes, Later suppression, the More hint, reader deferral, download action and live speed in Arabic/English, light/dark. Android hardware installer coverage remains unavailable.
